I built a single Mule 4 application (assessment-application.xml) behind an APIKit router with a RAML contract, together with a shared DataWeave module (transformUtils.dwl) and a MySQL database. The API covers eleven tasks: JSON/XML transformation with metadata, XML namespaces and null-safe mapping; file-based order loading with validation, data cleansing, masking, audit logging and error tracking; a scheduled customer job; a backend integration; and a Batch Job for large order files. Because later tasks change the behaviour of earlier ones, older tasks keep their own versioned paths (/v1/...) while newer ones use the base or /v2 paths, so earlier results stay stable. To avoid repetition I moved shared logic into sub-flows (file loading, record cleansing, audit logging, backend call) and a global error handler that gives every error the same {error, message} shape. Configuration is environment-based, with secrets protected by secure properties.

On top of the functional work I added operational controls. The transform endpoint has a rate limit of 100 requests per minute (429 when exceeded) and a 5 minute cache keyed by an MD5 of the request, using Object Stores. The backend endpoint is protected by idempotency (10 minutes), a retry with exponential waits of 1, 2 and 4 seconds, and a circuit breaker that opens after 3 consecutive failures, fails fast with 503, and tests the backend again after 60 seconds before closing. Order processing records every file in an audit table, writes failed rows to an error table, and uses a batch update-then-insert so that rows are not duplicated even though the table has no unique key. The submission contains the project source, the SQL setup and an export of the database with the test data, and a video walkthrough.
